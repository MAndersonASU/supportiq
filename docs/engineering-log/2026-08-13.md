# 2026-08-13 — Project bootstrap

## Goal

Stand up the repository and project skeleton before any pipeline work
begins.

## Decisions

- **Project**: SupportIQ — a customer support ticket platform combining a
  data pipeline, an ML triage classifier, and a Claude-powered RAG
  resolution assistant.
- **Scope**: local-first development; a cloud deploy is planned only at the
  end, for the demo.
- **LLM provider**: Claude API, for the retrieval-augmented generation
  layer in Phase 3.
- **Dataset**: Kaggle's "Twitter Customer Support" dataset — real
  brand-support exchanges on Twitter. Preferred over more structured,
  pre-labeled ticket datasets because the raw text requires real parsing,
  labeling, and cleaning work, which better reflects a production data
  pipeline.
- **Repo**: [MAndersonASU/supportiq](https://github.com/MAndersonASU/supportiq),
  public, MIT licensed.

## Ingestion pipeline

### Goal

Acquire the raw dataset and build the ingestion stage: a schema-enforced,
memory-bounded pipeline from raw CSV to a landing-zone Parquet file.

### Completed

- Pulled `twcs.csv` (2,811,774 rows, 516 MB) from Kaggle's
  `thoughtvector/customer-support-on-twitter` dataset into `data/raw/`.
- Defined the raw record schema as a Pydantic model (`src/data/schema.py`,
  `RawTweet`): tweet ID, author ID, inbound flag, timestamp, text, and the
  two response-linkage fields, with parsing for Twitter's date format and
  comma-separated ID lists.
- Built the ingestion pipeline (`src/data/ingest.py`): streams the raw CSV
  in 50k-row chunks, validates each row against `RawTweet`, and writes
  conformant rows to `data/landing/tweets.parquet`. Malformed rows are
  counted and skipped rather than failing the run.
- Added a unit test (`tests/test_ingest.py`) covering both a valid record
  and a malformed one, run against a small in-memory fixture rather than
  the full dataset.
- Ran the pipeline end-to-end against the full dataset: 2,811,774 rows
  read, 2,811,774 written, 0 rejected, in 56 seconds.
- Added `requirements.txt` and `pyproject.toml` (pytest configuration),
  and extended `.gitignore` to exclude the landing zone alongside raw and
  processed data.

### Next steps

Add the validation stage: business-rule checks (allowed value ranges,
cross-field consistency) on top of the structural schema already enforced
during ingestion, and produce the first validated dataset in
`data/processed`.

## Validation pipeline

### Goal

Add business-rule validation on top of the structural schema from
ingestion, and produce the first validated dataset.

### Completed

- Evaluated Great Expectations for this stage; its dependency chain
  requires a numpy build with no prebuilt wheel for the current Python
  version. Switched to Pandera, which covers the same DataFrame-validation
  need without that build overhead.
- Defined a Pandera schema (`src/data/validate.py`) enforcing hard
  business rules: `tweet_id` uniqueness, non-empty `author_id`/`text`, and
  a plausible `created_at` window (2006-03-21 onward, pre-2020).
- Added two soft quality metrics, computed but not enforced as rejections:
  the rate of `in_response_to_tweet_id` values with no matching tweet in
  the dataset, and the count of duplicate `(author_id, text)` pairs.
- Added `tests/test_validate.py`, covering each hard-check failure mode
  independently and confirming the two soft metrics are recorded without
  dropping rows.
- Ran validation against the full landing-zone dataset: 2,811,774 rows in,
  0 rejected, 3,862 broken response links (0.19%), 4,732 duplicate
  author/text pairs. Output written to `data/processed/tweets.parquet`,
  with `data/processed/validation_report.json` committed to the repo as a
  record of data quality at this stage.

### Next steps

Cleaning stage: text normalization and a defined policy for the
duplicate-pair and missing-value cases the validation report surfaced.

## Cleaning pipeline

### Goal

Normalize text for downstream use, enforce the missing-value policy, and
resolve the duplicate-pair question left open by validation.

### Completed

- Split the single `data/processed` output into two tiers:
  `data/validated` (business-rule-passed, from the validation stage) and
  `data/processed` (final, cleaned). The two were previously conflated
  under one directory, which made it ambiguous whether cleaning had run.
- Investigated the ~4,700 duplicate `(author_id, text)` pairs flagged by
  validation before writing any dedup logic. Each has a distinct, unique
  `tweet_id` — they're a support account sending an identical templated
  reply to different customers, not duplicate records. No deduplication
  was implemented; removing them would have deleted legitimate distinct
  interactions.
- Built the cleaning stage (`src/data/clean.py`): Unicode NFKC
  normalization and whitespace collapse into a new `text_clean` column,
  original `text` preserved. Rows that are empty after normalization are
  dropped and counted. A defensive check confirms no unexpected nulls
  outside the two nullable response-linkage fields.
- Added `tests/test_clean.py` covering normalization, the empty-after-
  cleaning drop, and both branches of the null-field check.
- Ran the full pipeline (ingest → validate → clean) end to end against the
  real dataset: 2,811,774 rows in, 2,811,774 out, 0 dropped, 0 unexpected
  nulls. Final dataset at `data/processed/tweets.parquet`, report at
  `data/processed/cleaning_report.json` (committed).

Phase 1.

## Feature engineering and data versioning

### Goal

Reconstruct tweet-level data into ticket-level records and put the result
under DVC version control, closing out Phase 1.

### Completed

- Built `src/features/build_ticket_features.py`: resolves each tweet's
  reply chain to its root using an iterative find-with-path-compression
  (union-find), groups by thread, and aggregates into one row per
  customer-initiated ticket (message counts, first responder, time to
  first response, opening-message text stats). Brand-initiated threads
  are excluded — they aren't support interactions.
- Fixed a duplicate-column bug caught immediately by running against the
  real dataset: the original `text` field and the renamed `text_clean`
  both resolved to `text` before the raw column was dropped first.
- Added `tests/test_build_ticket_features.py`: chain resolution across
  multi-message threads, broken-link handling, resolved vs. unresolved
  tickets, and exclusion of brand-initiated threads.
- Ran against the full processed dataset: 2,811,774 tweets → 798,197
  threads → 789,547 tickets.
- Two findings surfaced and documented rather than silently carried
  forward: `resolved` is constant (100% True) on this dataset because of
  how it was originally collected, so it isn't a usable ML signal as
  defined; and the dataset has no `category`/`priority` ground truth,
  meaning Phase 2 needs a labeling strategy before it can train a
  supervised classifier. `first_response_seconds` also has a long-tailed
  outlier (max ~7.7 years) that Phase 2 will need to handle explicitly.
- Installed DVC, initialized it in the repo, and configured a local
  filesystem remote outside the OneDrive-synced project folder (to avoid
  double-syncing large data). Tracked `ticket_features.parquet` (83 MB) —
  the expensive-to-regenerate final artifact — and pushed it to the
  remote. Larger intermediate tiers are left untracked since they're
  fully reproducible by re-running the pipeline.

Data engineering phase complete: ingestion, validation, cleaning, feature

## Phase 2: weak-supervision labeling

### Goal

Resolve the labeling gap from Phase 1: the dataset has no ground-truth
`category` or `priority`, and no supervised classifier can be trained
without one.

### Completed

- Evaluated LLM-based labeling (Claude Haiku 4.5) as the original plan.
  Blocked at the account level — no billing credits available, and
  purchasing API credits is a real-money decision outside this project's
  budget. Pivoted to a zero-cost approach: weak supervision instead of an
  LLM call.
- Ran an exploratory clustering pass (TF-IDF + LSA + KMeans,
  `src/models/explore_categories.py`) to ground the category taxonomy in
  the actual data rather than guessing. First pass clustered on raw text
  and mostly rediscovered *brand* (Delta, Apple, Amazon...), not issue
  type — expected in hindsight, since brand vocabulary dominates a
  multi-company dataset, and it's already captured by `brand_id`. Stripped
  brand handles and anonymized customer IDs before re-clustering; the
  resulting clusters aligned with real issue-type vocabulary
  (account/password/access, order/delivery, flight delays, app glitches,
  service-quality complaints).
- Rejected raw cluster assignment as the label itself: silhouette scores
  stayed low (0.05–0.09) across every cluster count tested, and roughly
  half the sample fell into one linguistically generic cluster KMeans
  couldn't usefully subdivide. Used the clusters' top terms to calibrate
  keyword labeling functions instead (`src/models/label_tickets.py`) —
  word-boundary keyword matching per category, highest-scoring category
  wins, default to `General Inquiry` when nothing matches.
- Found and fixed an apostrophe-encoding bug before trusting the output:
  ~16% of tickets use a typographic apostrophe (`'`, U+2019) instead of
  ASCII `'`, silently breaking contraction keywords like `"won't load"`.
  Added normalization; the fix barely moved the label distribution,
  confirming the real cause of the large default-category bucket is that
  most short tweets simply don't contain explicit category vocabulary —
  a genuine limitation of keyword-based weak supervision on short,
  informal text, not a bug.
- Built `assign_priority`: urgency-keyword count, exclamation marks, and
  ALL-CAPS words scored into Low/Medium/High. Deliberately reads ticket
  text only — never `first_response_seconds` or any other post-open
  outcome field, since building a label from an outcome a model might
  later be trained to predict would leak that outcome into its own
  target.
- Added `tests/test_label_tickets.py`: one case per category's keyword
  routing, the default-category fallback, a word-boundary false-positive
  guard, the apostrophe-normalization regression, and all three priority
  buckets.
- Ran against the full 789,547-ticket dataset (free and local, so no
  sample-size limit the way the LLM approach would have had): 22.6%
  positively categorized across six specific categories, 77.4% default
  `General Inquiry`; priority split 75% Low / 19.6% Medium / 5.4% High.
  Output at `data/processed/labeled_tickets.parquet`, report at
  `data/processed/labeling_report.json` (committed).

### Next steps

Train a baseline classifier (category, priority) on the weak labels, with
train/val/test splits and MLflow experiment tracking.

## Phase 2: baseline classifiers

### Goal

Train and evaluate a baseline model for category and for priority on the
weak-supervision labels, with a proper stratified split and MLflow
experiment tracking rather than untracked ad hoc runs.

### Completed

- Built `src/models/split_data.py`: one stratified 70/15/15 train/val/test
  split, stratified on `category` (the more imbalanced target) and reused
  for both models, so a given ticket lands in the same partition for
  both. Added `tests/test_split_data.py` covering split proportions,
  full class coverage in every split, no duplicate assignment across
  splits, and determinism given a fixed random state.
- MLflow's plain filesystem tracking backend raised a maintenance-mode
  error on the installed version (3.15.1) — switched to the
  currently-recommended SQLite backend (`sqlite:///mlflow.db`) rather
  than opting out of the warning.
- Built `src/models/train_classifier.py`: TF-IDF + logistic regression
  (`class_weight="balanced"`) for category and for priority, each logged
  to MLflow against a majority-class `DummyClassifier` baseline. Added
  `tests/test_train_classifier.py` for the metrics helper (perfect
  predictions score 1.0, per-class stats are plain Python types so the
  report JSON-serializes cleanly).
- Ran against the full dataset (552,682 train / 118,432 val / 118,433
  test): category test macro F1 0.977, priority test macro F1 0.421.
- Investigated both numbers before trusting them rather than reporting
  them as "the model works." Category's near-perfect, uniformly-high
  score (0.94–0.997 across all seven classes) is the signature of
  reconstructing a deterministic function, not learned generalization —
  expected, since TF-IDF word features overlap almost completely with the
  keyword phrases that define the labels, and no independent ground truth
  exists to check real generalization against. Priority's weaker score
  has a specific, mechanistic cause: part of the priority label depends
  on exclamation marks and ALL-CAPS words, which scikit-learn's default
  `TfidfVectorizer` strips before tokenizing — that signal is structurally
  invisible to the model. Chose not to add those as explicit features,
  since doing so would just reproduce category's circularity rather than
  add real generalization. Also found `class_weight="balanced"` pushing
  hard on the rare High-priority class: precision 0.115, recall 0.447 —
  a real cost of balancing against a 75/20/5 label split, left for the
  hyperparameter-tuning stage.
- Models saved to `models/{category,priority}_classifier.joblib`
  (gitignored, reproducible by re-running the script) and logged as
  MLflow artifacts. Evaluation report at
  `data/processed/model_evaluation_report.json` (committed).

### Next steps

Hyperparameter tuning and a more deliberate evaluation pass — particularly
the High-priority precision problem — followed by a model registry stage
with explicit staging → production promotion criteria.
