# 2026-08-13 — Project bootstrap

## Goal

Stand up the repository and project skeleton before any pipeline work
begins.

## Decisions

- **Project**: SupportIQ — a customer support ticket platform combining a
  data pipeline, an ML triage classifier, and a Claude-powered RAG
  resolution assistant.
- **Scope**: local-first development; a cloud deploy is planned only at the
  end, for the demo.
- **LLM provider**: Claude API, for the retrieval-augmented generation
  layer in Phase 3.
- **Dataset**: Kaggle's "Twitter Customer Support" dataset — real
  brand-support exchanges on Twitter. Preferred over more structured,
  pre-labeled ticket datasets because the raw text requires real parsing,
  labeling, and cleaning work, which better reflects a production data
  pipeline.
- **Repo**: [MAndersonASU/supportiq](https://github.com/MAndersonASU/supportiq),
  public, MIT licensed.

## Ingestion pipeline

### Goal

Acquire the raw dataset and build the ingestion stage: a schema-enforced,
memory-bounded pipeline from raw CSV to a landing-zone Parquet file.

### Completed

- Pulled `twcs.csv` (2,811,774 rows, 516 MB) from Kaggle's
  `thoughtvector/customer-support-on-twitter` dataset into `data/raw/`.
- Defined the raw record schema as a Pydantic model (`src/data/schema.py`,
  `RawTweet`): tweet ID, author ID, inbound flag, timestamp, text, and the
  two response-linkage fields, with parsing for Twitter's date format and
  comma-separated ID lists.
- Built the ingestion pipeline (`src/data/ingest.py`): streams the raw CSV
  in 50k-row chunks, validates each row against `RawTweet`, and writes
  conformant rows to `data/landing/tweets.parquet`. Malformed rows are
  counted and skipped rather than failing the run.
- Added a unit test (`tests/test_ingest.py`) covering both a valid record
  and a malformed one, run against a small in-memory fixture rather than
  the full dataset.
- Ran the pipeline end-to-end against the full dataset: 2,811,774 rows
  read, 2,811,774 written, 0 rejected, in 56 seconds.
- Added `requirements.txt` and `pyproject.toml` (pytest configuration),
  and extended `.gitignore` to exclude the landing zone alongside raw and
  processed data.

## Feature engineering and data versioning

### Goal

Reconstruct tweet-level data into ticket-level records and put the result
under DVC version control, closing out Phase 1.

### Completed

- Built `src/features/build_ticket_features.py`: resolves each tweet's
  reply chain to its root using an iterative find-with-path-compression
  (union-find), groups by thread, and aggregates into one row per
  customer-initiated ticket (message counts, first responder, time to
  first response, opening-message text stats). Brand-initiated threads
  are excluded — they aren't support interactions.
- Fixed a duplicate-column bug caught immediately by running against the
  real dataset: the original `text` field and the renamed `text_clean`
  both resolved to `text` before the raw column was dropped first.
- Added `tests/test_build_ticket_features.py`: chain resolution across

## Phase 2: weak-supervision labeling

### Goal

Resolve the labeling gap from Phase 1: the dataset has no ground-truth
`category` or `priority`, and no supervised classifier can be trained
without one.

### Completed

- Evaluated LLM-based labeling (Claude Haiku 4.5) as the original plan.
  Blocked at the account level — no billing credits available, and
  purchasing API credits is a real-money decision outside this project's
  budget. Pivoted to a zero-cost approach: weak supervision instead of an
  LLM call.
- Ran an exploratory clustering pass (TF-IDF + LSA + KMeans,
  `src/models/explore_categories.py`) to ground the category taxonomy in
  the actual data rather than guessing. First pass clustered on raw text
  and mostly rediscovered *brand* (Delta, Apple, Amazon...), not issue
  type — expected in hindsight, since brand vocabulary dominates a
  multi-company dataset, and it's already captured by `brand_id`. Stripped
  brand handles and anonymized customer IDs before re-clustering; the
  resulting clusters aligned with real issue-type vocabulary
  (account/password/access, order/delivery, flight delays, app glitches,
  service-quality complaints).
- Rejected raw cluster assignment as the label itself: silhouette scores
  stayed low (0.05–0.09) across every cluster count tested, and roughly
  half the sample fell into one linguistically generic cluster KMeans
  couldn't usefully subdivide. Used the clusters' top terms to calibrate
  keyword labeling functions instead (`src/models/label_tickets.py`) —
  word-boundary keyword matching per category, highest-scoring category
  wins, default to `General Inquiry` when nothing matches.
- Found and fixed an apostrophe-encoding bug before trusting the output:
  ~16% of tickets use a typographic apostrophe (`'`, U+2019) instead of
  ASCII `'`, silently breaking contraction keywords like `"won't load"`.
  Added normalization; the fix barely moved the label distribution,
  confirming the real cause of the large default-category bucket is that
  most short tweets simply don't contain explicit category vocabulary —
  a genuine limitation of keyword-based weak supervision on short,
  informal text, not a bug.
- Built `assign_priority`: urgency-keyword count, exclamation marks, and
  ALL-CAPS words scored into Low/Medium/High. Deliberately reads ticket
  text only — never `first_response_seconds` or any other post-open
  outcome field, since building a label from an outcome a model might
  later be trained to predict would leak that outcome into its own
  target.
- Added `tests/test_label_tickets.py`: one case per category's keyword
  routing, the default-category fallback, a word-boundary false-positive
  guard, the apostrophe-normalization regression, and all three priority
  buckets.
- Ran against the full 789,547-ticket dataset (free and local, so no
  sample-size limit the way the LLM approach would have had): 22.6%
  positively categorized across six specific categories, 77.4% default
  `General Inquiry`; priority split 75% Low / 19.6% Medium / 5.4% High.
  Output at `data/processed/labeled_tickets.parquet`, report at
  `data/processed/labeling_report.json` (committed).

### Next steps

Train a baseline classifier (category, priority) on the weak labels, with
train/val/test splits and MLflow experiment tracking.

## Phase 2: baseline classifiers

### Goal

Train and evaluate a baseline model for category and for priority on the
weak-supervision labels, with a proper stratified split and MLflow
experiment tracking rather than untracked ad hoc runs.

### Completed

- Built `src/models/split_data.py`: one stratified 70/15/15 train/val/test
  split, stratified on `category` (the more imbalanced target) and reused
  for both models, so a given ticket lands in the same partition for
  both. Added `tests/test_split_data.py` covering split proportions,
  full class coverage in every split, no duplicate assignment across
  splits, and determinism given a fixed random state.
- MLflow's plain filesystem tracking backend raised a maintenance-mode
  error on the installed version (3.15.1) — switched to the
  currently-recommended SQLite backend (`sqlite:///mlflow.db`) rather
  than opting out of the warning.
- Built `src/models/train_classifier.py`: TF-IDF + logistic regression
  (`class_weight="balanced"`) for category and for priority, each logged
  to MLflow against a majority-class `DummyClassifier` baseline. Added
  `tests/test_train_classifier.py` for the metrics helper (perfect
  predictions score 1.0, per-class stats are plain Python types so the
  report JSON-serializes cleanly).
- Ran against the full dataset (552,682 train / 118,432 val / 118,433
  test): category test macro F1 0.977, priority test macro F1 0.421.
- Investigated both numbers before trusting them rather than reporting
  them as "the model works." Category's near-perfect, uniformly-high
  score (0.94–0.997 across all seven classes) is the signature of
  reconstructing a deterministic function, not learned generalization —
  expected, since TF-IDF word features overlap almost completely with the
  keyword phrases that define the labels, and no independent ground truth
  exists to check real generalization against. Priority's weaker score
  has a specific, mechanistic cause: part of the priority label depends
  on exclamation marks and ALL-CAPS words, which scikit-learn's default
  `TfidfVectorizer` strips before tokenizing — that signal is structurally
  invisible to the model. Chose not to add those as explicit features,
  since doing so would just reproduce category's circularity rather than
  add real generalization. Also found `class_weight="balanced"` pushing
  hard on the rare High-priority class: precision 0.115, recall 0.447 —
  a real cost of balancing against a 75/20/5 label split, left for the
  hyperparameter-tuning stage.
- Models saved to `models/{category,priority}_classifier.joblib`
  (gitignored, reproducible by re-running the script) and logged as
  MLflow artifacts. Evaluation report at
  `data/processed/model_evaluation_report.json` (committed).

### Next steps

Hyperparameter tuning and a more deliberate evaluation pass — particularly
the High-priority precision problem — followed by a model registry stage
with explicit staging → production promotion criteria.

## Phase 2: hyperparameter tuning

### Goal

Sweep regularization strength and class weighting for both classifiers,
with proper validation-based model selection, and determine whether the
High-priority precision problem is a tunable hyperparameter issue or
something more fundamental.

### Completed

- Built `src/models/tune_classifier.py`: a small grid over `C` (0.1, 1.0,
  10.0) and `class_weight` (`None`, `balanced`) for both targets. The
  vectorizer is fit once per target and reused across the grid rather
  than refit per trial, since vectorizing 550k+ documents is the
  expensive step and only the classifier changes between configurations.
  Selection uses validation macro F1 exclusively; the test set is scored
  once per target, after the winning configuration is fixed.
- Caught a real convergence issue before trusting the first tuning run:
  `lbfgs` failed to converge within the original 200-iteration cap at
  higher `C` values. Raised `max_iter` to 1000 for both the baseline and
  tuning stages and reran both — the baseline numbers were unaffected
  (already converging cleanly at the default `C`), confirming the
  original untuned results were valid, while the tuning run completed
  cleanly with no warnings.
- Tuned results: category test macro F1 0.987 (`C=10`, `class_weight=
  balanced`) — a marginal gain over the untuned 0.977, consistent with a
  task that's already near its ceiling. Priority test macro F1 0.428
  (`C=0.1`, `class_weight=balanced`) — also a marginal gain over 0.421.
- Ruled out "wrong hyperparameter" as the explanation for priority's
  High-priority precision problem: `class_weight=balanced` wins on
  validation macro F1 at every `C` tested but one, and the tuned model's
  High-priority precision (0.119) is effectively unchanged from the
  untuned baseline (0.115). The real cause is the feature gap already
  identified in the baseline stage (punctuation/casing signal invisible
  to the default tokenizer), not a hyperparameter this grid could fix.
- Added `tests/test_tune_classifier.py` for the trial-selection logic:
  correct argmax by validation macro F1, and deterministic tie-breaking.
- Report at `data/processed/tuning_report.json` (committed); tuned
  models overwrite `models/*_classifier.joblib` (gitignored,
  reproducible).

### Next steps

Model registry stage: explicit staging → production promotion criteria,
and versioning for the tuned models.

## Phase 2: model registry

### Goal

Register the tuned classifiers in the MLflow Model Registry with an
explicit, code-defined promotion policy, closing out Phase 2.

### Completed

- Checked the installed MLflow version's registry API before writing
  promotion logic against it: the older stage-transition API
  (`transition_model_version_stage`) is legacy in favor of registry
  aliases. Built `src/models/register_model.py` on aliases
  (`staging`/`production`) rather than the deprecated path.
- Defined the promotion policy as a pure function
  (`decide_promotion`), separate from the MLflow read/write calls: a
  version reaches `staging` only with at least a 0.05 absolute macro F1
  lift over its majority-class baseline, and reaches `production` only
  if it also matches or beats the current production version, or none
  exists yet.
- Added `tests/test_register_model.py` covering all four decision paths:
  rejected for insufficient lift, promoted directly with no incumbent,
  promoted by matching or beating one, held at staging on regression.
  Caught a floating-point boundary bug in the first version of one test
  (`0.30 + 0.05 - 0.30` doesn't reliably equal exactly `0.05`) — not a
  bug in the promotion logic, fixed by testing clearly-above/below
  values instead of an exact boundary.
- Ran against both tuned models: category (lift +0.86) and priority
  (lift +0.14) both cleared the staging threshold by a wide margin, and
  both promoted directly to production as first versions with no
  incumbent to compare against. Verified the aliases resolve correctly
  against the live registry after the run.
- Report at `data/processed/registry_report.json` (committed).

## Phase 3: RAG resolution assistant (local stack)

### Goal

Build the retrieval-augmented resolution assistant without the Claude
API, since the Anthropic account has no billing credits and purchasing
credits is outside this project's scope to decide unilaterally.

### Completed

- Installed Ollama and pulled Llama 3.2 3B (2 GB) as the local
  generation model, and added `sentence-transformers` (local embeddings)
  and `chromadb` (local vector store) to the stack. No external API
  calls anywhere in this stage.
- Built `src/ai/build_knowledge_base.py`: reconstructs thread structure
  against the full cleaned tweet dataset (reusing the tested
  `assign_thread_roots` from feature engineering) to pair each labeled
  ticket's opening message with the first brand reply in its thread —
  the actual resolution text, which `ticket_features.parquet` doesn't
  carry. All 789,547 tickets resolved successfully. Added
  `tests/test_build_knowledge_base.py` covering correct pairing by
  timestamp and dropping tickets with no reconstructable reply.
- Benchmarked embedding speed before committing to a full run: the full
  789,547-entry knowledge base measured at roughly an hour on CPU, for a
  dataset that's 77% one category. Built
  `src/ai/build_vector_index.py` with a per-category cap (15,000 max,
  smaller categories keep everything) instead, cutting the indexed set
  to 96,536 entries and the build to about nine minutes while keeping
  every category represented for retrieval. Disabled Chroma's anonymous
  telemetry, consistent with the earlier DVC decision. Added
  `tests/test_build_vector_index.py` for the capping logic.
- Built `src/ai/rag_assistant.py`: embeds a new ticket, retrieves the
  top-k nearest past tickets from the vector index, and prompts the
  local LLM to draft a grounded reply citing the ticket(s) it drew on.
  Added `tests/test_rag_assistant.py` for prompt construction.
- Ran the full pipeline against real queries before considering it
  done, and caught a real grounding failure on the first one: the model
  copied a tracking URL verbatim from a retrieved example into its
  draft — a different customer's link. Fixed by explicitly instructing
  the prompt not to copy links, order numbers, case numbers, or
  usernames from the examples. Re-ran the same query after the fix;
  the copied identifier was gone. A second query (a technical-support
  case) also retrieved relevant grounding and produced a coherent
  drafted reply. Known, accepted limitation: the model occasionally
  echoes structural labels like `Support reply:` from the prompt into
  its output — a small-model formatting quirk, not a grounding problem,
  not worth over-engineering the prompt to eliminate.
- Reports at `data/processed/knowledge_base_report.json` and
  `data/processed/vector_index_report.json` (committed). The knowledge
  base parquet and the Chroma vector store itself are gitignored and
  reproducible by re-running the two build scripts.

### Next steps

Structured output for the drafted reply (so it's a typed object a
serving layer can consume, not free text), an evaluation harness for
generation quality, and — if useful — a lightweight routing agent on
top of the classifiers and the resolution assistant.

## Phase 3: structured output, evaluation, and end-to-end triage

### Goal

Move the RAG assistant from free text to a validated structured
response, build an evaluation harness that doesn't rely on a paid
judge, and tie the Phase 2 classifiers together with the Phase 3
resolution assistant into one triage pipeline.

### Completed

- Added a Pydantic `ResolutionDraft` model (`reply`,
  `cited_ticket_ids`, `needs_human_escalation`) and switched
  `rag_assistant.py` to Ollama's JSON-schema-constrained output
  (`format=ResolutionDraft.model_json_schema()`), replacing free-text
  parsing with a validated object.
- Extracted `verify_citations` as a pure function: any ticket ID the
  model claims to have cited is cross-checked against what was actually
  retrieved, and dropped if it wasn't. Added unit tests for the accept,
  reject, and no-citation cases.
- Built `src/ai/evaluate_rag.py`: six fixed test queries scored on
  hallucinated-citation rate, reply non-emptiness, and embedding-based
  groundedness (cosine similarity between the reply and the retrieved
  resolutions it's grounded in). Deliberately does not use the local
  LLM to judge its own output — self-judging is a known-unreliable
  technique, and there's no independent judge available without a paid
  API. Added tests for the pure cosine-similarity and summarization
  logic (no model loading required, so the suite stays fast).
- First evaluation run found a real hallucination: 1 of 6 queries
  produced citations to tickets that were never retrieved, caught and
  dropped by `verify_citations` before reaching the caller. This is the
  safety net doing its job on a real failure, not defensive code for a
  hypothetical one. Mean groundedness similarity was 0.51 — a moderate
  score, which is the right outcome: a very high score would suggest
  the model is copying retrieved text rather than paraphrasing it.
- Built `src/ai/triage_pipeline.py`, combining the Phase 2 classifiers
  and the Phase 3 resolution assistant into one classify-then-draft
  call. Models load via their MLflow registry `production` alias
  (`models:/<name>@production`) rather than the local `.joblib` files
  directly, so the registry is actually consulted at inference time.
- Hit and fixed a real dependency-interaction bug while wiring this
  together: `mlflow.sklearn.load_model` defaults to `skops`
  serialization, and `skops`'s type-introspection triggers a
  `transformers` lazy-import chain requiring `torchvision` — but only
  once `sentence-transformers` has already been imported earlier in the
  same process, which the triage pipeline does by importing the RAG
  assistant. Switched model logging to `pickle` serialization (a
  reasonable choice for models this project trained itself, versus
  `skops`'s protection against untrusted third-party models) and
  re-registered both classifiers as new versions.
- Ran the fixed pipeline against a live ticket and found a second real
  finding, this time evidence rather than a bug: a ticket containing
  "crashing" was classified `General Inquiry` instead of `Technical
  Support`, because the category keyword pattern `\bcrash\b` doesn't
  match "crashing" (no word boundary between "crash" and "ing"), and
  the classifier inherited this blind spot along with the labeling
  rule's accuracy. Recorded as concrete evidence for the earlier
  "classifier reconstructs the rule, not true understanding" finding
  rather than fixed — a fix would mean re-running all of Phase 2.
- Report at `data/processed/rag_evaluation_report.json` (committed).

### Next steps

Phase 4 (MLOps/serving): FastAPI endpoints wrapping the triage pipeline,
Docker packaging, CI/CD, and basic monitoring/logging.

## Phase 4: FastAPI service and structured logging

### Goal

Wrap the triage pipeline in a FastAPI service with a health check,
structured request logging, and a testable API layer that doesn't
require the live model stack to run its own tests.

### Completed

- Built `src/serving/app.py`: `GET /health` and `POST /triage`, with
  Pydantic request/response models giving automatic validation and
  `/docs`. The triage function is injected via a FastAPI dependency
  rather than imported and called directly, so `tests/test_serving_app.py`
  swaps in a fake function and tests routing, validation, and response
  shaping without Ollama, the vector index, or the MLflow registry
  available.
- Deliberately skipped eager model loading at startup — `triage_pipeline`
  and `rag_assistant` already lazily load and cache their models, so
  duplicating that as FastAPI startup warm-up would have forced the
  `TestClient` (which runs the app's lifespan on construction) to load
  real models just to build a test client for the fake-dependency tests.
- Built `src/serving/logging_config.py`: a JSON log formatter so log
  lines are parseable fields, not free text. Request logs carry path,
  method, status code, and duration; the triage-specific log records
  `text_length` and the predictions, never the raw ticket text — a
  support ticket can carry customer-identifying content, and a log file
  is a much less controlled surface than the API response.
- Added `tests/test_logging_config.py` for the formatter (valid JSON
  output, extra fields merged in correctly).
- A new deprecation warning appeared during testing: Starlette's
  `TestClient` now recommends `httpx2` over `httpx`. Verified it's a
  real, actively published package before switching rather than
  ignoring the warning or switching on faith — confirmed and adopted it.
- Ran the actual server (not just the mocked test suite) end to end:
  started uvicorn, hit `/health`, sent a real ticket to `/triage`, and
  confirmed the response, the structured logs (including that ticket
  text was correctly absent from them), and `/docs` all worked. First
  request took about 14 seconds — the documented, expected cost of
  lazy-loading the embedding model, vector index, and classifiers on
  first use rather than at startup.

### Next steps

Docker packaging (the service plus a way to reach Ollama, likely
docker-compose given the local-LLM dependency) and CI/CD via GitHub
Actions.
